## 2. New findings

### Medium

**M1: The N2 fix is incomplete. A valid signature whose signing-certificate-v2 names a certificate that is
not in the CMS certificate set (typically the root) is still reported INVALID, with no identity**
(`pdfsignaturereport.cpp:140-151`). Proven.
- Probe: `signWithChainAttribute` with `CMS_add1_cert(cms, m_root)` left out. The attribute names
  [good signer, root]; the certificate set holds only the signer. The program's own signer accepted the file.
- Report: `isIntegrityValid false`, `chain 0`, errors `("Trusted certificate not found.", "No certificate in
  the signature is the one named by its signed attributes and verifying it.")`, PAdES level `"B-B"`.
- The control run, `verificationReportChainInSigningCertificate` (root included), passes.
- Leaving the root out of the CMS is normal practice: the root comes from the verifier's trust store.
  RFC 2634 5.4 / RFC 5035 require only the first ESSCertID to identify the signing certificate.
- The CMS certificate set is unsigned. Anyone who handles the file can also strip a certificate the
  attribute names and turn a valid signature into "INVALID".

Scenario: a counter-party's genuine PAdES signature from a provider that lists the chain in the attribute.
Andre's report for a dispute shows it as INVALID, with no signer.

Fix: decide the signer by the first ESSCertID(v2) only. With the opaque OpenSSL 3 types there are two ways:
- a minimal DER parse of the first element (hash algorithm, hash, optional issuerSerial), compared with
  the candidate;
- retry `OSSL_ESS_check_signing_certs` with the CMS set, the `/DSS /Certs` and the trusted roots added
  after the candidate.

The probe showed that the return code (`0` against `-1`) cannot tell "a later ID is missing" from
"the first ID does not match": a lone decoy also returns `0`. Do not use the return code to decide.
Add a "root not shipped" case to the test.

### Low

**L1: Two signer-controlled strings in the report are still not cleaned** (`pdfsignaturereport.cpp:496`,
`:570`, `:576`). Reading.
- `item.fieldName` (the `/T` text string, which may be UTF-16 with U+202E) is printed as the "Field" row.
- `timestampAuthority` is the subject of a TSA certificate the other party embedded, printed in the
  "Trusted timestamp ... by %2" and "Timestamp authority" rows. Only `clean()` stops a right-to-left
  override; HTML escaping does not.

Fix: `clean()` both, or apply `clean()` once inside `Helper::row`.

**L2: Named-field selection takes the last of several fields with that name and does not check that the
signature is the one just written** (`pdflongtermvalidation.cpp:503-511`). Reading. Exploiting this needs a
planted field with the same millisecond name, which is not practical. A malformed file with two fields of
the same fully qualified name (the PDF spec forbids it, the parser accepts it) would still be resolved by
document order alone.

Fix (cheap defence in depth): refuse more than one match, and require the matched signature's last byte
range to end at `signedDocument.size()`.

**L3: N3 loose ends** (`pdflongtermvalidation.cpp:445`, `:606-622`). Reading.
- (a) The CRL check has no clock-skew tolerance. A CRL issued "now" by a CA whose clock is a few
  seconds ahead of the PC is refused as "out of date". OCSP gets 300 s.
- (b) When OCSP answered "good" and the CRL was refused (expired `nextUpdate`, wrong signer), the
  CRL's error message is still discarded. R3 asked for it to be kept as a warning.
- (c) No regression test pins the new rules.

Fix:
- `X509_cmp_time(lastUpdate, now + 300 s) < 0`;
- `result.warnings << crlErrorMessage` when the CRL was refused but OCSP answered;
- two test cases: a CRL 10 days old with `nextUpdate` in the future is accepted; an OCSP answer with
  `nextUpdate` and a `thisUpdate` 10 days old is accepted.

**L4: `existingStoreIsKept` is flaky** (`UnitTests/tst_longtermvalidationtest.cpp:247-255`, `:655`). Proven.
- It failed once in my first full run: `second.crlCount` was 1, expected 0. It passed on 6 single reruns.
- The test CA builds a new CRL on every request with `lastUpdate = now`, which has 1-second resolution.
  When the two `addValidationData` calls fall in different seconds the CRL bytes differ, so it counts as
  new. The production code is not at fault.

Fix: cache the CRL in `TestCertificationAuthority`, or build it with a fixed `lastUpdate`.

### Checked and found sound

- No regression at any call site. Each signing flow passes the name of the field it created. A rewrite
  after `IncrementalUpdateFailed` keeps the same name. `extend()` with an unknown name stores nothing and
  still adds the document timestamp over the untouched signed bytes. `checkExtendedFile` and the
  saved-file check use the same name.
- The timestamp-only path (`pdf4qt_timestamp_*`) walks the TSA chain of the token, which is what the user chose.
- `getRemaining` never passes 0 or a negative timeout (`qMax(1, ...)`). `QDeadlineTimer(60000)` is
  finite, so `remainingTime()` is never -1.
- `clean()` removes Cc, Cf, Zl and Zp, which covers bidi overrides and isolates.
- The essprobe matrix shows a decoy cannot be lifted by certificates added to the chain (table row above).
