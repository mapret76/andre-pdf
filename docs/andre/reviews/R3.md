## 2. New findings

### Medium

**N1 - The "newest signature" selection is hijacked by an earlier signature with a bogus `/ByteRange`
end; the hostile party's certificates are walked and the signature just made gets no validation data**
(`pdflongtermvalidation.cpp:500-517`) - proven.
`newest` is the field with the largest `offset + size` over all signature fields. The value is read from
the file, not checked against it. Probe: a document signed first with the revoked test certificate, then
(incremental update) with the good one; the first signature's last range value rewritten to `9999999`
(same width, the file is 14 866 bytes). `addValidationData` returned `ok true`, `revokedCertificates
("/CN=Andre PDF test signer (revoked)")`, `certificateCount 2` - the earlier signature's chain was walked
and stored; the control run on the untouched file walked only the good certificate. Consequences: (a) the
M6 fix is defeated by exactly the party it excludes (the other signer's OCSP/CRL/CA-issuer URLs are
contacted, 60 s, 3 redirects to any host); (b) the certificate of the signature the user just made is not
stored, no OCSP/CRL for it, while the dialog says "long-term validation data embedded: 2 certificates ...";
the saved file's format line then reads B-T, which is the only visible hint.
Scenario: a counter-party sends a contract carrying their signature with an inflated range end (nothing
else about it needs to be valid; Andre PDF does not refuse to sign a file with an invalid existing
signature). Andre signs with LTV on: his own signature ends up without long-term data.
Fix: select the signature whose ranges end exactly at `signedDocument.size()` (the one just written
covers the whole file) and ignore any range with `offset + size > signedDocument.size()`; better, let the
caller pass the field name it just created (`extend` is called right after `sign` in both flows) and
walk that field only. Add the probe as a test.

**N2 - A legitimate signature whose signing-certificate-v2 attribute lists the chain is reported INVALID
and without identity** (`pdfsignaturereport.cpp:142`) - proven.
`OSSL_ESS_check_signing_certs(ss, ssv2, chain, 0)` requires the i-th ESSCertID to match the i-th element
of `chain`; the code passes a one-element stack. RFC 5035 section 3 lets the attribute carry the
certification path after the signer's certificate, and signers do (OpenSSL's own
`OSSL_ESS_signing_cert_v2_new_init` takes a chain; several CA signing services include it). Probe: a
CAdES signature by the good test certificate with an ESS v2 attribute holding the signer and the root
(`CMS_add1_signer` + `CMS_signed_add1_attr_by_NID`, the program's own signer accepted the file, result 0).
Report: `integrity false`, `chain 0`, errors `("Self-signed certificate in chain.", "No certificate in
the signature is the one named by its signed attributes and verifying it.")`.
Scenario: a third party's valid PAdES signature from such a provider is shown to Andre as "INVALID",
with no name, in the report he gives to a court.
Fix: check only the first ESSCertID / ESSCertIDv2 against the candidate (hash with the attribute's
algorithm, `issuerSerial` if present), or build `chain` from the pool in order (signer, issuer, ...)
before calling `OSSL_ESS_check_signing_certs`. Add the two-id case to the decoy test.

**N3 - The 7-day `lastUpdate` rule refuses valid CRLs; monthly-CRL CAs never get revocation data, and
the refusal is silent when OCSP answered** (`pdflongtermvalidation.cpp:437-444`, `:609-626`) - reading.
R2-A M1 asked for "reject a CRL whose `nextUpdate` has passed". The fix also requires
`lastUpdate > now - 7 days`. RFC 5280 defines validity by `nextUpdate`; many CAs issue CRLs weekly,
fortnightly or monthly (government and enterprise CAs commonly monthly). Such a CRL is "out of date" to
this code every day after the seventh: for a CRL-only certificate no revocation data is stored (no
B-LT); for an OCSP certificate the CRL is dropped, so the program's own panel is back to "Unable to get
CRL" - and the warning `crlErrorMessage` is discarded because `status` is already Good (`:620-626`). The
same 7-day `maxsec` applies to OCSP `thisUpdate` even when `nextUpdate` is still in the future (RFC 6960
says such an answer is valid; several CAs pre-produce 7-10 day answers).
Fix: CRL: require `lastUpdate <= now < nextUpdate` only; OCSP: pass `maxsec = 7 d` only when
`nextUpdate` is absent (`OCSP_check_validity` twice, or check `nextUpdate` by hand); keep the CRL
warning in `result.warnings` when the CRL is refused although OCSP answered.

### Low

**N4 - The one-minute budget is not a bound** (`:547-551`, `:272`, `:337`, `:418`) - reading.
`getTimeout()` is evaluated once per call; `fetchIssuer`, `getOcspResponse` and `getCrl` each loop over
every URI of the certificate with that same timeout, so one certificate with k AIA + m OCSP + n CRL URIs
can take (k+m+n) x 15 s. Certificates beyond the 32nd are skipped without a warning (`:551`). Fix: pass
the deadline, not a timeout, and check it per URI; warn when certificates are left unwalked.

**N5 - Redirects still go to any host** (`:179`) - reading. `NoLessSafeRedirectPolicy` with 3 hops; the
destination (loopback, RFC 1918, link-local) is unrestricted. R2-A M6 named this; R2-fixes does not list
it as open. Fix: `UserVerifiedRedirectPolicy` to the original host, as the update checker does.

**N6 - TSA fallback only in "Sign Digitally"** (`signatureplugin.cpp:1264-1278`; USER-GUIDE.md section
4) - reading. The contract-pack loop reports each part as failed when the TSA is down; the guide says
"the program offers to sign without a timestamp" without qualification. Fix: ask once before the loop,
or qualify the guide.

**N7 - Signature-dictionary strings are not cleaned** (`pdfsignaturereport.cpp:490-493`, `:681-691`) -
reading. `/Name`, `/Reason`, `/Location`, `/ContactInfo` are signer-controlled and printed without
`clean()`; a right-to-left override in `/Reason` reverses the row in the browser and the saved PDF. Fix:
`clean()` them too.

**N8 - Identity and trust rows can describe different certificates** (`:159-180` vs
`pdfsignaturehandler.cpp:1180`) - reading. The report binds the identity to the ESS attribute; the
upstream verifier still takes the first certificate by issuer and serial for `isIntegrityValid` /
`isCertificateTrusted`. With a decoy first (the test's `withSigner` case) the identity is the real one and
the trust row is the decoy's (untrusted). Only a downgrade is possible, so no gain for an attacker;
but a trusted signer can be shown "NOT trusted" by someone who edits the certificate set. Fix: pass the
ESS-bound certificate to the verifier, or make the verifier apply the same check.

**N9 - Proxy only after the first LTV request** (`pdflongtermvalidation.cpp:174`;
`pdfcertificatemanager.cpp` TSA request) - reading. See the L10 row. Fix: set it once at application
start (R2-A's suggestion), remove it from `request()`.

**N10 - `.p7c` bundle: first name match wins** (`:288-299`) - reading. If the first `X509_check_issued`
match (same name/key id) does not verify the certificate (cross-certificate with another key), the other
bundle members are never tried. Fix: test `X509_verify` inside the loop.

### Checked and found sound

- `.p7c` OpenSSL ownership (`X509_up_ref` before `PKCS7_free`, `X509_free` on the failure path); the
  `stored` and `responders` pools free their references; `pool.add(storedIssuer)` takes its own.
- `isSignerCertificate`: `CMS_SignerInfo_set1_signer_cert(si, cert)` then `(si, nullptr)` leaves no
  leak; `ERR_clear_error()` after; a candidate with the right issuer/serial but another key fails
  `CMS_SignerInfo_verify`; with no signed attributes the check degrades to issuer/serial (non-PAdES only).
- `isGapOnlySignature` cannot read out of bounds: the lexer caps integers at `INT64_MAX/100`, ranges
  with negative sizes or an end beyond the file are refused before any index (probe with a crafted file).
- Stale data: OCSP without `nextUpdate` older than 7 days and a CRL with `nextUpdate` in the past are
  refused (test passes; the runtime output of the probes matched).
- The signed bytes are still untouched: `startsWith` guards in `addValidationData` and `extend`.
- Stamp: the elision character U+2026 is drawn through `QPainter` with an embedded TrueType subset, so
  it renders; the stamp height follows the line count.
- TSA fallback: the second `sign` reuses the same parameters (fingerprint already cleared if the first
  attempt had fallen back to a full rewrite), `isTimestampSkipped` suppresses the extension, the save
  dialog then reads "format: PAdES baseline B-B".
- `onVerificationReport` try/catch restores the cursor before the message; "Save as PDF" reports an
  empty output file.
- ECT Act citations: s4(4) for Schedule 2 is right in both files now; s1 added for "process".

## 3. Are the "accepted" / "open" items honestly described?

Mostly yes. The open items (L1, L4, R1 L7/L8, L13) and the accepted ones (L6, L8, L9, M2 coverage,
B2-L6 remainder) are stated plainly. Three rows are more generous than the code:
- **M1 "fixed"**: the comparison with the signing time that the finding asked for is only in the
  report; the embed side still stores answers produced before the signature. The row admits it, but
  "fixed" should be "partly (report flags it)".
- **M6 "fixed"**: the redirect-to-any-host half of the finding is not addressed and not listed as open;
  the one-minute claim is not a bound (N4); and the selection itself is bypassable (N1).
- **L5 and L10 "fixed"**: only the single-signature flow has the TSA fallback; only OCSP/CRL/CA-issuers
  get the proxy, and only after the first LTV request.
- The ledger ticks B1, B2 and B3 `[x]`. The B1 gate (Windows-store signing with a real token, Acrobat
  / EU DSS check of a B-LTA file) is recorded, but it is the only path by which an accredited
  certificate can be used, and nothing produced by either path has been validated outside the
  program. Ticking B1 before that gate is a judgment call Andre should make knowingly; the ledger
  should say "ticked subject to the B1 gate".
